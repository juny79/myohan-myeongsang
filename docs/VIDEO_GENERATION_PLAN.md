# 묘한 명상 오픈소스 영상 생성 프로그램 종합계획서

> 문서 버전 1.1 · 대시보드 연동 컨트롤러의 현재 구현 범위와 다음 개발 단계를 반영했습니다.

## 1. 목적

묘한 명상의 기획·운영 대시보드와 연동되는 영상 생성 프로그램을 만든다. 프로그램은 기획 정보를 받아 장면별 생성 작업을 만들고, GPU 워커에서 클립을 생성한 뒤 사람이 승인한 클립과 사용 허가가 확인된 음원을 조립해 최종 영상을 출력한다.

지원할 실행 환경은 다음 세 가지다.

1. **로컬 PC:** NVIDIA RTX 3070, VRAM 8GB
2. **클라우드 GPU:** NVIDIA A100 MIG, 할당 VRAM 40GB
3. **클라우드 GPU:** NVIDIA H100 SXM, VRAM 80GB

목표는 장비마다 별도 프로그램을 만드는 것이 아니라, **공통 작업 명세·API·산출물 규격을 사용하고 GPU별 프로파일만 교체**하는 것이다. RTX 3070은 프리뷰와 경량 작업, A100 MIG는 표준 장면 생성, H100은 고품질·배치 작업을 담당한다.

## 2. 제품 원칙 및 범위

### 묘한 명상에 맞는 결과 원칙

- 고양이가 머무는 한국적 공간에 잠·휴식·집중용 소리를 더한다.
- 과한 카메라 이동보다 고정 구도와 느린 움직임을 우선한다.
- 고양이 행동은 장면당 하나의 단순한 행동으로 제한한다. (예: 눈을 감고 졸기, 꼬리를 천천히 움직이기)
- 깜빡임, 고양이의 얼굴·발·무늬 변형, 공간 왜곡, 갑작스러운 줌·컷, 번쩍임을 검수한다.
- 생성 모델에 글자나 로고를 만들게 하지 않는다. 필요한 글자는 영상 후처리에서 합성한다.
- 한 장면은 짧은 클립으로 생성한다. 30–150분 영상은 클립 생성, 반복·전환, 음악 조립으로 제작한다.
- 의료·치료 효과를 주장하지 않는다.

### 1차 범위

- 기존 대시보드에서 작업 생성·상태 확인·산출물 확인
- 장면 프롬프트 구성, 생성 요청, GPU 백엔드 선택
- 생성 클립 미리보기, 승인·반려·재생성
- 승인 클립 조립, 외부에서 권리 확인된 음악 결합, MP4 출력
- 작업 로그, 모델·라이선스·프롬프트·시드·GPU 정보 저장

### 1차 범위 밖

- 영상 파운데이션 모델을 처음부터 학습
- 미승인 음원 생성·자동 삽입 또는 Content ID 권리 판정
- 완성 영상의 YouTube 자동 업로드
- 사람의 창작·품질 검수를 제거하는 완전 자동 공개
- 개방형 인터넷에 GPU 워커나 파일 저장소를 노출

## 3. 기존 대시보드와의 통합 원칙

기존 `index.html`은 `data/board.json`을 읽는 대시보드이며, 브라우저의 `localStorage`는 화면 진행 상태에만 사용한다. 초기 연동을 위해 로컬 컨트롤러(`video_app/server.py`)와 영상 작업 패널을 추가했다. 현재 대시보드는 로컬 컨트롤러가 제공하는 작업 명세 생성·조회·취소 API를 호출하지만, 실제 모델 추론·GPU 워커·렌더링은 아직 연결되지 않았다. 다음 개발은 이 안정된 작업 명세/API 경계 뒤에 GPU 워커를 단계적으로 추가하는 방식으로 진행한다.

중요한 원칙은 프런트엔드에 GPU 자격증명·클라우드 키를 두지 않는 것, 브라우저의 임시 상태를 작업 원본으로 취급하지 않는 것이다. 생성 작업은 서버가 발급한 `jobId`와 저장된 작업 명세를 기준으로 추적한다.

### 통합 방식 선택

**권장 1차 방식: 같은 저장소 안의 API 서버와 정적 대시보드**

- `index.html`은 화면·사용자 입력만 담당한다.
- FastAPI 같은 백엔드는 REST API로 작업 생성, 조회, 취소, 승인, 렌더 요청을 제공한다.
- 백엔드는 DB/작업 큐에 요청을 저장하고 대상 GPU 워커에 전달한다.
- 작업 목록·상태·산출물 경로는 서버가 관리한다. `board.json`은 초기 주간 기획 입력과 보드 기본값으로 유지한다.
- 개발 단계에서는 같은 PC에서 UI와 API를 같은 출처(origin)로 제공한다. 클라우드 도입 시 인증·HTTPS·CORS 정책을 명시적으로 구성한다.

정적 GitHub Pages는 백엔드 실행 공간이 아니므로 GitHub Pages에 HTML을 게시하는 것만으로 GPU 생성이 동작하지 않는다. 공개 대시보드는 로그인 없는 운영 콘솔로 만들지 않는다. 초기에는 로컬 네트워크/인증된 사용자만 API에 접근하도록 제한한다.

### 데이터 흐름

1. 운영자가 대시보드에서 `data/board.json`의 영상 아이템을 선택한다.
2. **생성 작업 만들기**를 누르고 영상 기둥·공간·길이·화면비·품질 프리셋·음악 파일(선택)을 확인한다.
3. 브라우저가 작업 명세를 백엔드에 전송한다. 서버는 필수값·권한·모델 라이선스 상태를 확인하고 `jobId`를 돌려준다.
4. 큐가 `local_preview`, `standard_scene`, `premium_scene` 중 선택된 프로파일에 적합한 워커로 작업을 보낸다.
5. 워커는 장면 클립 및 로그를 저장하고 진행 이벤트를 API로 보고한다.
6. 대시보드는 `jobId` 기준으로 상태를 갱신한다. 첫 버전은 3–5초 간격 폴링을 사용하고, 필요하면 이후 SSE/WebSocket으로 바꾼다.
7. 운영자가 프리뷰를 검수해 승인·반려한다. 승인 전에는 최종 렌더에 포함하지 않는다.
8. 렌더 요청이 승인 클립을 FFmpeg로 조립한다. 최종본·작업 요약·모델 정보가 대시보드에 표시된다.
9. 운영자가 최종 파일과 라이선스·설명란 체크를 확인하고 수동 공개한다.

### API 범위

현재 로컬 MVP 구현:

| 메서드·경로 | 기능 |
|---|---|
| `GET /api/v1/health` | 컨트롤러 상태 및 선택적 `nvidia-smi` 탐지 |
| `GET /api/v1/jobs` | 최근 작업 명세 목록 조회 |
| `POST /api/v1/jobs` | 보드 영상 항목에서 작업 명세 생성·저장 |
| `POST /api/v1/jobs/{jobId}/cancel` | 아직 실행 전인 `draft` 작업 취소 |

다음 API는 향후 단계에서 구현한다.

| 메서드·경로 | 기능 |
|---|---|
| `GET /api/v1/jobs/{jobId}` | 단일 작업의 상태·진행률·로그 요약 조회 |
| `GET /api/v1/jobs?itemId=...` | 보드 아이템별 작업 이력 조회 |
| `POST /api/v1/jobs/{jobId}/cancel` | 실행 중인 워커에 취소 요청 전달 |
| `POST /api/v1/jobs/{jobId}/clips/{clipId}/review` | 클립 승인·반려 및 코멘트 저장 |
| `POST /api/v1/jobs/{jobId}/render` | 승인된 클립으로 최종 영상 조립 |
| `GET /api/v1/jobs/{jobId}/artifacts` | 프리뷰·최종 파일·메타데이터 링크 조회 |
| `GET /api/v1/workers` | 워커 연결 여부, GPU 종류, 가용 상태 조회 |

API는 요청 검증, 사용자 인증, 크기 제한, 취소와 오류 처리, 제한된 파일 다운로드를 갖춘다. 브라우저에 임의 파일 경로나 임의 셸 명령을 전달하지 않는다.

### 작업 상태 모델

`draft → queued → preparing → generating → review → rendering → completed`

오류·취소 상태는 `failed`, `cancelled`로 분리한다. 항목의 제작 상태(`예정/제작중/예약/완료/보류`)와 GPU 작업 상태는 서로 다른 개념이므로 별도로 저장한다. 성공한 GPU 작업이 곧 공개 완료를 뜻하지 않는다.

대시보드의 아이템에는 `itemId`를 유지하고, 생성 작업은 별도 작업 테이블/JSON 저장소에 기록한다. 로컬 `localStorage`는 화면 환경설정만 보관한다. 공동 작업에 필요한 진행 정보는 서버에서 관리한다.

## 4. GPU 환경별 역할과 프리셋

모델의 최소 VRAM 수치는 모델 버전·정밀도·해상도·프레임 수·추론 구현에 따라 달라진다. 아래 사양은 출발 목표이며, 실제 호환성은 대상 장비에서 실행 시험을 통과한 설정만 지원 대상으로 등록한다.

| 환경 | 역할 | 시작 프리셋 | 기본 전략 |
|---|---|---|---|
| RTX 3070 8GB | 로컬 기획·구도 프리뷰 | 16:9 또는 9:16, 480p급, 4–8초, 동시 1개 | 경량·양자화 모델, 이미지→영상 우선, 저정밀·오프로딩 선택 |
| A100 MIG 40GB | 표준 본편 장면 | 16:9, 720p급 목표, 5–10초, 동시 1개부터 | 중간 크기 모델, MIG 실측, 품질/시간 균형 |
| H100 SXM 80GB | 고품질·배치 장면 | 720p–1080p 목표, 5–10초, 동시성 실측 후 설정 | 큰 체크포인트 비교, 다중 시드·배치 렌더 |

### RTX 3070 8GB

주 역할은 본편 장시간 생성이 아니라 프롬프트·구도 확인, 짧은 클립, 정지 키비주얼에 미세한 움직임을 더하는 이미지→영상이다. 해상도·프레임 수를 낮추고 배치 1부터 시작한다. GPU 메모리 부족 시 자동 축소 또는 명확한 실패를 반환하고 무한 재시도하지 않는다.

### A100 MIG 40GB

운영 전에 40GB MIG가 실제로 어떤 A100 장치/프로파일인지 확인한다. 예를 들어 80GB A100의 MIG 분할 중 40GB 프로파일은 해당 분할 리소스를 할당받는 것이지 전체 카드의 연산 자원을 단독으로 받는다는 뜻이 아니다. 워커 시작 시 GPU 이름, MIG 장치, 가시 메모리, CUDA·드라이버를 기록한다. 5–10초 장면의 처리 시간과 성공률을 측정한 뒤 동시성을 결정한다.

### H100 SXM 80GB

큰 체크포인트, 높은 품질 설정, 장면 배치 렌더를 우선 시험한다. 1080p가 모델 네이티브 품질을 보장한다고 가정하지 않는다. 고해상도 업스케일은 생성 해상도와 구분해 기록한다. H100도 파운데이션 모델 전체 학습 장비로 쓰지 않으며, 필요 시 승인된 데이터와 목적에 한해 LoRA를 별도 검토한다.

## 5. 오픈소스 모델 조사·선정·권리관리

초기 후보군은 경량·중간·대형 모델을 각각 소수 선정해 비교한다. 예를 들어 공개 코드/가중치가 있는 Wan 계열, LTX-Video 계열, CogVideoX 계열 등을 조사 후보로 둘 수 있다. 이 문서는 특정 체크포인트의 상업적 사용을 승인하지 않는다.

모델별로 다음을 기록한다.

- 모델·체크포인트 정확한 이름/버전, 공식 출처, 다운로드 시점, 파일 해시
- 코드 라이선스와 가중치 라이선스 각각의 조건
- 상업 이용, 배포·파생, 저작자 표시, 제한 용도와 별도 약관
- 추론 코드 및 주요 의존성의 라이선스
- 사용 CUDA·PyTorch·드라이버, 정밀도·양자화 구성
- 각 GPU별 성공률, 최대 VRAM, 생성시간, 출력 품질과 실패 원인
- 승인 담당자, 검토 일자, 미해결 질문

“오픈소스” 또는 공개 가중치라는 이유만으로 유튜브 수익화·상업적 이용이 가능하다고 간주하지 않는다. 모델별 버전의 라이선스를 검토하고, 조건이 모호한 것은 내부 테스트에 한정하거나 채택하지 않는다. 음원 라이선스와 생성 모델 라이선스는 별도 게이트다.

## 6. 생성·조립 파이프라인

1. **기획 입력:** 기둥(M/S/F/C), 사용 상황, 공간, 시간·날씨, 고양이 행동, 음악 결, 영상 길이, 공개 형식.
2. **장면 분해:** 긴 영상 전체를 생성하는 대신 4–10초 클립의 장면 목록으로 변환한다. 장면별 프롬프트, 금지 요소, 구도, 움직임, 시드, 모델 프리셋을 저장한다.
3. **프리뷰 생성:** 저비용 프리셋으로 장면 한두 개 생성. 인물·고양이 외형과 고정 구도를 검증한다.
4. **본 생성:** 승인된 장면만 선택 GPU에서 생성한다. 재시도는 실패 유형·시드 변경 사유를 기록한다.
5. **기술 검사:** 파일 존재·길이·해상도·프레임 손상·검은 프레임·오디오 유무 확인.
6. **사람 검수:** 고양이 형태, 플리커, 갑작스러운 움직임, 분위기, 반복 이음새 확인. 불합격 클립은 최종 편집에서 제외한다.
7. **조립:** 승인된 클립을 순서·속도·전환 규칙에 따라 FFmpeg로 반복/연결한다. 전환은 느리고 눈에 띄지 않게 한다.
8. **음악 결합:** 사용권이 확인된 음원만 결합한다. 크레딧 요구사항과 파일 ID를 작업에 연결한다.
9. **마스터 출력:** 채널의 해상도·프레임률·오디오 목표에 맞는 MP4 출력, 검수용 프리뷰와 최종본 분리.
10. **공개 게이트:** 영상 제목·썸네일·설명, 음원 권리·크레딧, 의료 효능 표현, Content ID 위험을 사람이 확인한 뒤 수동 공개.

최종 영상 길이는 반복 클립의 총 길이만으로 품질을 판단하지 않는다. 루프 경계에서 화면·소리의 급격한 단절이 없는지 확인한다. 현재 전략의 기본값(명상 30–45분, 수면 90–180분)을 우선 지원하고, 10시간 동일 루프는 기본 프리셋으로 제공하지 않는다.

## 7. 저장·보안·운영

- 작업 산출물은 `jobId/itemId` 기준으로 분리한다. 원본 프롬프트, 로그, 프리뷰, 최종본, 메타데이터를 구분한다.
- 개인 PC는 초기에는 로컬 저장을 기본으로 한다. 클라우드 파일은 비공개 버킷·서명 URL·보존기간·삭제 정책을 둔다.
- API 키와 SSH 키는 브라우저, JSON, Git 저장소에 저장하지 않는다. 환경변수/비밀관리 기능을 사용한다.
- GPU 워커는 승인된 작업 큐만 소비하고, 공개 요청에서 셸 명령이나 arbitrary model path를 받지 않는다.
- 사용자 로그인 또는 로컬 단일 사용자 접근 제한, 요청 크기·동시성·시간 제한을 설정한다.
- 작업 취소, 워커 비정상 종료, GPU OOM, 파일 전송 중단에 대한 재시작·실패 기록을 둔다.
- 모델 파일은 출처와 해시를 확인하고, 업데이트 전 회귀 테스트한다.

## 8. 구축 단계와 완료 조건

### 0단계 — 요구사항·환경 확인

RTX 3070 OS/드라이버/CUDA, A100 MIG 제공 방식, H100 접속 방식, 저장 위치, 예산·보존 정책을 확정한다. 세 장비의 네트워크 접근과 파일 전송 방법도 결정한다.

**완료 조건:** 장비별 접근·권한·GPU 메모리 식별 방법 및 초기 모델 권리검토 양식 확정.

### 1단계 — 로컬 컨트롤러와 대시보드 작업 명세 연동 (현재 구현)

저장소에 `video_app/server.py`를 두고 외부 패키지 없는 로컬 HTTP 컨트롤러를 제공한다. `index.html`에 GPU 프리셋 선택, 선택 아이템 작업 명세 등록, 컨트롤러/GPU 상태 표시, 작업 목록, 대기 작업 취소 기능을 추가한다. 생성 명세는 로컬 SQLite에 저장하고 DB는 Git에 포함하지 않는다.

현재 단계는 **모델 없는 통합 스켈레톤**이다. 작업 상태는 `draft`/`cancelled`만 저장한다. GPU 프리셋 선택은 라우팅 메타데이터일 뿐 실제 GPU 렌더링을 수행하지 않는다. 대시보드가 백엔드 서버에서 제공될 때 동일 출처 API 호출이 동작하며, GitHub Pages는 이 로컬 API를 대신 제공하지 않는다.

**완료 조건:** 로컬 주소에서 대시보드와 API가 함께 열림, API 연결 상태 표시, 영상 보드 아이템으로 작업 등록·목록 표시·취소, SQLite 영속성 확인. 영상 파일이 생성되지 않는 상태를 UI에서 명확히 표시.

### 2단계 — RTX 3070 단일 장면 추론 PoC

RTX 3070에서 승인 후보 하나로 4–8초 프리뷰를 생성하고 파일·로그·실패 처리를 확인한다. 간단한 FFmpeg 조립 CLI를 만든다. GPU 워커는 현재 API의 작업 ID·프리셋·작업 상태 규약을 사용한다.

**완료 조건:** 같은 입력 명세로 재현 가능한 작업, 명확한 OOM 오류, 프리뷰 MP4 산출.



### 3단계 — RTX 3070 실제 생성 워커

실제 Windows/Linux OS, NVIDIA 드라이버, CUDA, Python 버전과 RTX 3070 장비에서 먼저 환경 점검한다. 상업 이용 조건이 검토된 후보 모델 하나를 선정하고, 짧은 장면 프롬프트에서 생성하는 워커 인터페이스를 붙인다. VRAM·시간·성공률을 기록하고 OOM·취소·모델 미설치 오류를 사용자에게 표시한다.

**완료 조건:** 승인 모델로 짧은 프리뷰 클립 한 개를 로컬에서 생성하고, 작업 목록의 상태가 대기→생성→검수로 이동하며 클립 경로와 생성 로그를 확인할 수 있음.

### 4단계 — A100 MIG 및 H100 워커

장비별 워커를 공통 작업 큐에 연결한다. MIG 프로파일·가시 VRAM·드라이버 정보를 확인하고, 모델/프리셋별 성능을 측정한다. 외부 GPU와 로컬 컨트롤러 간 연결은 인증된 네트워크와 제한된 포트로 구성한다. 작업 중복 실행과 동시성 제한을 적용한다.

**완료 조건:** 같은 작업 명세가 세 GPU 대상에서 추적되고, 장비별 생성 시간·최대 메모리·실패 사유가 기록되며 미지원 프리셋은 실행 전에 차단됨.

### 5단계 — 검수·조립

클립 검수 UI(승인/반려/재생성 코멘트)를 완성한다. 승인된 영상만 FFmpeg 조립 입력으로 허용하고, 반복·전환·오디오 페이드·출력 규격을 처리한다. 결과물마다 모델·시드·음원 크레딧 메타데이터를 남긴다.

**완료 조건:** 짧은 승인 클립과 권리 확인된 테스트 오디오로 검수용 MP4 생성, 기술 검사와 사람 검수 통과.

### 6단계 — 파일럿 및 운영 강화

쇼츠용 짧은 파일럿부터 제작한다. 고양이 외형 일관성, 깜빡임, 루프 경계, 렌더 시간, 수정 횟수를 기록하고 프롬프트·프리셋을 보정한다. 인증, 보관·삭제, 백업, 비용 제한과 오류 복구를 점검한 뒤에만 긴 영상에 확대한다.

**완료 조건:** 재현 가능한 파일럿 제작 체크리스트, 영상별 권리·모델 정보, 롤백·삭제 절차가 문서화됨.

## 9. 현재 구현 상태와 바로 확인할 수 있는 것

- `video_app/server.py`: 로컬 컨트롤러, 최소 API, SQLite 작업 명세 저장, 선택적 `nvidia-smi` 탐지.
- `index.html`: 대시보드 하단에 초기 영상 생성 연동 패널과 GPU 프리셋 선택 추가.
- `video_app/README.md`: 실행 및 현재 기능/제한 안내.
- `runtime/`: 로컬 작업 DB 저장 위치. Git 제외 대상.
- 실제 영상 모델, 클립 생성, 큐 워커, FFmpeg 렌더링은 **아직 구현되지 않음**.

로컬 실행은 프로젝트 루트에서 `py video_app/server.py` (또는 `python video_app/server.py`)를 실행한 뒤 `http://127.0.0.1:8765/`를 여는 방식이다. GitHub Pages는 정적 페이지만 호스팅하므로 이 API와 GPU를 실행하지 않는다.

## 10. 첫 파일럿 성공 기준

첫 시험은 45분 본편이 아니라 20–30초 쇼츠용 장면 한 개로 시작한다.

1. 보드에서 `w1-wed` 또는 다른 영상 아이템을 선택한다.
2. 로컬 컨트롤러에서 작업 명세가 생성되고 브라우저 새로고침 후에도 목록에 남는지 확인한다.
3. RTX 3070 워커 구현 후, 4–8초 클립이 생성되어 프리뷰로 표시되는지 확인한다.
4. 고양이 형태·플리커·급격한 움직임·장면 톤을 사람이 승인한다.
5. 생성시간, 최대 VRAM, 수정 횟수와 라이선스 검토 결과를 기록한다.
6. 이상이 없을 때만 짧은 쇼츠 렌더와 A100/H100 비교로 확장한다.

첫 단계의 작업 등록 성공은 영상 생성 성공과 다르다. 화면에서 실제 추론이 준비되지 않았다고 표시되면 정상적인 단계 구분이며, 다음 구현은 RTX 3070의 OS·드라이버·모델 선정 정보가 확보된 뒤 시작한다.
